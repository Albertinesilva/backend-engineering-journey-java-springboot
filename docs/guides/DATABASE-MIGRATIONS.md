## 1. O que é uma migration

Uma **migration** é um script SQL versionado que muda o banco: cria uma tabela, adiciona uma restrição, insere dados. O **Flyway** aplica as migrations em ordem de versão ao subir a aplicação e anota as que já aplicou numa tabela própria do banco, a `flyway_schema_history`. Na subida seguinte, ele aplica só as migrations novas.

O nome do arquivo segue o padrão do Flyway. Em `V001__create_table_category.sql`:

- `V` indica uma migration versionada;
- `001` é a versão;
- `__` (dois sublinhados) separa a versão da descrição;
- `create_table_category` é a descrição.

## 2. Nunca altere uma migration já aplicada

Para cada migration aplicada, o Flyway grava na `flyway_schema_history` um **checksum**: um número calculado a partir do conteúdo do arquivo. A cada subida, ele recalcula o checksum dos arquivos e compara com o gravado. Se um arquivo já aplicado foi editado, os números não batem e a subida falha.

Por isso, uma mudança no banco deve ser feita numa migration nova. Editar uma migration aplicada só é aceitável num banco local que você vai recriar do zero (seção 7).

Neste capítulo, as migrations V001 a V004 têm conteúdo diferente do capítulo 02, e a V004 mudou de nome. Um banco criado pelo capítulo 02 não serve para este capítulo: é preciso recriá-lo.

## 3. Pastas e versões

As migrations ficam em `backend/src/main/resources/db/migration`, em duas pastas:

| Pasta | Conteúdo |
| --- | --- |
| `schema` | Estrutura do banco: tabelas e chaves |
| `data` | Dados de exemplo |

| Versão | Pasta | Arquivo | O que faz |
| --- | --- | --- | --- |
| V001 | `schema` | `create_table_category` | Cria `tb_category`, com `name` obrigatório e único (até 80 caracteres) |
| V002 | `schema` | `create_table_product` | Cria `tb_product`, com `name` obrigatório e único |
| V003 | `schema` | `create_table_product_category` | Cria a tabela de junção `tb_product_category` |
| V004 | `schema` | `alter_table_product_category` | Chaves estrangeiras de `tb_product_category` para `tb_category` e `tb_product` |
| V005 | `schema` | `create_table_role` | Cria `tb_role` |
| V006 | `schema` | `create_table_user` | Cria `tb_user`, com `email` obrigatório e único |
| V007 | `schema` | `create_table_user_role` | Cria a tabela de junção `tb_user_role` |
| V008 | `schema` | `alter_table_user_role` | Chaves estrangeiras de `tb_user_role` para `tb_role` e `tb_user` |
| V100 | `data` | `insert_categories` | 15 categorias |
| V101 | `data` | `insert_products` | 25 produtos |
| V102 | `data` | `insert_product_category` | 37 vínculos entre produtos e categorias |
| V103 | `data` | `insert_user` | 2 usuários: `albert@gmail.com` e `maria@gmail.com` |
| V104 | `data` | `insert_role` | 2 roles: `ROLE_OPERATOR` e `ROLE_ADMIN` |
| V105 | `data` | `insert_user_role` | 3 vínculos: albert com OPERATOR; maria com OPERATOR e ADMIN |

Uma **chave estrangeira** (*foreign key*) é a restrição que obriga um id a existir na tabela referenciada. É ela que impede apagar uma categoria que ainda tem produtos (resposta 409).

As migrations de estrutura deste capítulo estão no formato que o Hibernate gera a partir das entidades (`bigint generated by default as identity`, restrições com nomes como `FK5r4sbavb4nkd9xpl0f095qs2a`).

Os vínculos (V102 e V105) usam ids fixos e dependem de os registros receberem os ids 1, 2, 3... na ordem de inserção.

**Senha dos usuários de exemplo.** A V103 grava o hash BCrypt da senha `123456`. Esses usuários existem **só para desenvolvimento**; veja [AUTHENTICATION.md](AUTHENTICATION.md#3-login).

## 4. O que roda em cada perfil

| Perfil | Flyway | Resultado |
| --- | --- | --- |
| `dev` (padrão) | Ligado: `spring.flyway.locations=classpath:db/migration/schema,classpath:db/migration/data` | Estrutura e dados de exemplo no PostgreSQL |
| `test` | Desligado (`spring.flyway.enabled=false`) | O Hibernate cria as tabelas e o `import.sql` insere os dados (seção 5) |
| `prod` | Não configurado | Veja Limitações conhecidas |

## 5. O import.sql do perfil test

O perfil `test` usa o banco **H2 em memória**, criado vazio a cada subida, e desliga o Flyway. Nesse caso, o Hibernate cria as tabelas a partir das entidades e, logo depois, executa o arquivo `backend/src/main/resources/import.sql`.

O `import.sql` tem 84 comandos `INSERT`, os mesmos das migrations da pasta `data`: 15 categorias, 25 produtos, 37 vínculos de produto, 2 usuários, 2 roles e 3 vínculos de usuário. Assim, o perfil `test` tem os mesmos dados do perfil `dev`, inclusive os usuários para login.

O `import.sql` só é executado quando o Hibernate cria as tabelas. No perfil `dev` (`ddl-auto=none`), ele é ignorado.

Os testes também dependem desses dados: ids, totais e os usuários usados para obter tokens. Veja [TESTING.md](TESTING.md#7-factories-e-dados-de-exemplo).

## 6. O arquivo create.sql

O arquivo `backend/create.sql` fica fora da pasta `src` e **não é lido pela aplicação**. Neste capítulo, ele contém só o SQL de criação das seis tabelas e das chaves estrangeiras, no formato gerado pelo Hibernate; não tem mais os comandos `INSERT`.

As propriedades que geram esse tipo de arquivo (`jakarta.persistence.schema-generation.*`, com `create-target=create.sql`) estão comentadas no `application-test.properties`.

## 7. Recriar o banco de dev do zero

Útil depois de editar uma migration localmente, ou ao trocar de branch. **Apaga todos os dados do banco `asjcatalog`.**

> O banco `asjcatalog` tem o mesmo nome nos outros capítulos, mas a estrutura é diferente em cada um. Se ele foi criado por outra branch, o Flyway deste capítulo encontra um histórico de migrations que não corresponde aos arquivos daqui. Recrie o banco vazio antes de subir no perfil `dev`.

1. Pare a aplicação. O PostgreSQL não apaga um banco com conexões abertas.
2. Apague e crie o banco (o comando é igual no PowerShell e no bash):

   ```powershell
   psql -U postgres -c "DROP DATABASE asjcatalog;"
   psql -U postgres -c "CREATE DATABASE asjcatalog;"
   ```

3. Suba a aplicação no perfil `dev` (veja [GETTING-STARTED.md](GETTING-STARTED.md#4-caminho-completo-perfil-dev-com-postgresql)). O Flyway encontra o banco vazio e aplica todas as migrations, da V001 à V105.

## 8. Limitações conhecidas

- **Acentos corrompidos no perfil `test`.** O `import.sql` está em UTF-8, mas o `application-test.properties` não informa ao Hibernate a codificação do arquivo. Em Windows com JDK 17, em que a codificação padrão da JVM é `Cp1252`, as descrições em português aparecem trocadas. Nas migrations do Flyway, os acentos aparecem corretos. A propriedade `spring.jpa.properties.hibernate.hbm2ddl.charset_name=UTF-8`, que resolve isso, chega no capítulo 04.
- **Perfil `prod` sem configuração de banco e de Flyway.** O `application-prod.properties` só configura logs. A separação que impede os dados de exemplo em produção chega no capítulo 04.
- **O `import.sql` é mantido à mão.** Nada garante que ele continue igual às migrations da pasta `data`; ao mudar os dados de exemplo, atualize os dois.
- **O `create.sql` pode ficar desatualizado.** Ele não é gerado automaticamente a cada build.
- **Flyway não roda com o perfil `test`.** Um erro de SQL numa migration só aparece ao subir no perfil `dev`. Com o perfil `test`, usado para rodar a suíte, nenhum teste executa as migrations.
